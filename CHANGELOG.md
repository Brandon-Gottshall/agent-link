# Changelog

## Unreleased

### Breaking

The argument aliases and duplicated output keys that 0.5.0 deprecated (with a `deprecated_argument` warning) are removed, as announced (design doc sections 3.3 and 6.1 to 6.3, R6.1 to R6.4; PR B8). A removed argument is now an unknown property: the call fails with `invalid_arguments`, nothing runs, and the error's `hint` and `details.removed` (`[{argument, replacement}]`) name the replacement. Use the replacement names below. `allowTargetOverride` is not affected (it keeps working with a warning until 0.7.0).

- Removed argument aliases:
  - `list_codex_threads`: `searchTerm`. Use `query`.
  - `list_agent_link_receipts`: `searchTerm`. Use `query`.
  - `message_claude_session`: `body`. Use `message` (now `required` in the input schema).
  - `message_claude_session`: `to`. Use `sessionId` (exact id, archived sessions included) or `query` (fuzzy, archived sessions skipped). The exact-then-fuzzy fallback that `to` had is gone. Passing both `sessionId` and `query` is still `invalid_arguments`; its `details.errors[0].rule` is now `conflict` (was `alias_conflict`).
  - `reply_agent_link_message`: `body`. Use `message`.
  - `wait_for_claude_session`: `latestMessageId`. Use `replyToMessageId`.
  - `return_project_work_result`: `status`. Use `resultStatus` (now `required` in the input schema).
  - `agent_link_mailbox_inspect`: `since` as epoch milliseconds. `since` is now a string (ISO 8601) only; a number is `invalid_arguments` with a hint to pass an ISO timestamp.
- Removed duplicated output keys:
  - `wait_for_claude_session`: `result` (use `outcome`), `message` (use `reply`), and `sessionId` (use `target.sessionId`).
  - `message_claude_session` with `waitForReply`: `replyConfirmation`. Use `wait` (`wait.outcome`, `wait.reply`, `wait.reply.id`).
  - `message_codex_thread` with `waitForReply`, and the same result nested as `messageResult` in `message_project_orchestrator`, `return_project_work_result`, and `register_dependency_handoff`: `replyConfirmation`. Use `wait` (`wait.turn.finalResponse`, `wait.reply`, `wait.recentItems`, `wait.recentItemsEnvelope`). The 0.4-only `replyConfirmation` fields `enveloped` and `finalResponseItem` have no replacement. Receipts still record their `replyConfirmation` block.
- `tools/list`: the deprecated alias properties are no longer listed; `message_claude_session` lists `required: ["message"]` and `return_project_work_result` `required: ["resultStatus"]`. Internal: the registry no longer applies aliases (`applyAliases` and `deprecationWarning` are removed); a tool definition's `removedArguments` table only supplies the hint. The `tools/list` snapshots and the Codex golden replay are re-recorded (alias properties and `replyConfirmation` removed; the golden step that used `status` on `return_project_work_result` now passes `resultStatus`). New test `tests/server/removed-arguments.test.js`. The README, the `agent-link` skill, and `docs/testing.md` describe the removal.

### Other changes

- Fork and reconcile (design doc section 9.3, R9.7–R9.12; PR B7b fork). Uses the B7 spike results.
  - New tool `fork_codex_thread({threadId | query, message, model?, modelProvider?, serviceTier?, effort?, cwd?, lastTurnId?, compactFork?, reconcile?: {anticipation?, replyBy?}, archiveFork?, waitForResult?, timeoutMs?, receipt?})`. Use it to run another model, effort, or cwd on an existing thread's context.
    - It forks the thread through its latest completed turn (`thread/fork`, `threadSource: "agent-link-fork"`), optionally compacts the fork, and runs the enveloped task on the fork (`turnTrigger: "agent-link-fork"`, `clientUserMessageId` = the fork job id).
    - When the task's turn ends, it writes one reconcile message to the original thread's mailbox: `from` the caller, the requested `anticipation` (default `fyi`), and the final response as the body. The fork is then archived, unless `archiveFork: false`. The original never gets a turn with `model`, `effort`, or `cwd`, and is never compacted.
    - A failed or interrupted fork is reconciled too, with that status, and kept. `cwd` must stay inside the original's workspace (`cwd_outside_workspace`). A `claude:` target is `unsupported` (`capability: "fork"`).
  - A completed fork is archived only when it reports the original as `forkedFromId` and `threadSource: "agent-link-fork"`; otherwise it is kept with a `fork_archive_refused` warning.
  - **Envelope change.** A reconcile message carries `<fork thread model effort status/>` after `<overrides>`. A fork's task envelope has a fixed `<reply>` line saying its final response is the result.
  - Fork jobs live in `<state>/forks.jsonl`.
    - Only the server that started a job watches it live. It polls the fork's status without reading turns, backs off to 15 s, and wakes on `turn/completed`.
    - Every server runs a sweeper shortly after start and then every 60 s (only when the log exists), and stops it on shutdown. A lease (one server per job per minute) keeps the sweeps from multiplying.
    - The sweeper finishes jobs whose server stopped. That includes a reconcile message written but not finished (delivery, `reconciled`, archive and missing receipts, after 60 s). It also covers a task turn whose `turn/start` answer was lost: it is found by its `clientUserMessageId`, or failed and reconciled 15 minutes after the fork.
    - Claims keep it to one reconcile message per job, and are removed once the job is reconciled. A push holds a per-message claim; a sweep takes a push over only after 10 minutes. `reconciled` is written once, and only its writer archives and writes receipts.
    - A self-fork result counts as delivered only when the tool call actually returned it (`returned`). Otherwise a sweep makes it new mail again and pushes it, once, after the longest possible wait (11 minutes).
    - The job log's appends and compaction share a file lock (`src/shared/file-lock.js`, moved from the role table code), so compaction loses no event.
    - Past 512 KiB the log drops jobs finished more than 7 days ago.
    - Nothing is finished while no Agent Link server runs.
  - `agent_link_health` writes nothing. It reports `forkJobs: {pending, running, stuck, error}` from the job log.
  - Reconcile messages are queued for inbox pull until Codex push lands. Delivery is a single injected function (`deliver`) so push can be wired in.
  - `compactFork`: `auto` (default) compacts the fork when the original's last turn used more than half the model context window (spike: 0.5). The other values are `always` and `never`.
  - Token usage in receipts (R9.10). Fork receipts (`fork_thread`, `kind: "fork"`) record `tokenUsage: {compaction?, task}`. Reconcile receipts (`reconcile_fork`, `kind: "reconcile"`) record `tokenUsage: {delivery}`. `model-switch` / `effort-change` / `cwd-change` receipts record `override.tokenUsage.next` when `message_codex_thread` waited for the turn.
    - Usage is the sum of `last` over the turn's per-request `thread/tokenUsage/updated` notifications, plus `modelContextWindow` and `modelRequests`.
    - Missing usage after waiting is `null` with a `token_usage_unavailable` warning. A switch sent without `waitForReply` records `{next: null, reason: "not_waited"}` and warns nothing.
    - A `thread/settings/updated` that reports other values than requested adds `settings_mismatch`. A missing notification is not a mismatch.
    - Receipts link original and fork both ways (`original`, `fork`, `forkJobId`).
  - `list_agent_link_receipts` gains a `kind` filter (`fork`, `reconcile`, `model-switch`, `effort-change`, `cwd-change`). Receipt actions add `fork_thread` and `reconcile_fork`.
  - Expected cost (spike):
    - An effort change loses the prompt cache. Effort switches, including the launcher's, now report `expectedCost` like model switches (`last-turn-input` from recorded usage, else `unknown`).
    - A cwd change is cache-neutral: `{uncachedInputTokens: 0, basis: "cache-neutral"}`.
  - `agent_link_health` `codex.overrideCosts` reports the measured cache effect of overrides and forks (codex-cli 0.159.2). It warns (`override_costs_version_mismatch`) when the installed Codex differs.
  - The fork's caller is recorded as its launcher (`launchedBy`), so it may change the fork's effort.
  - Tests: `tests/codex/fork.test.js` (T-9.1, T-9.2, T-9.4–T-9.9, compaction decisions, per-request usage, stale interrupted usage, missing settings notification, already-archived fork; and the review fixes: self-fork timeout during the archive, recovery of a written but unfinished reconcile, a lost or missing task turn, sweeps that do not wait for usage, read-only health counts and shutdown stop, cheap owner polling and leased sweeps, claim cleanup and log compaction, compact tracker records, archive identity checks, a tracker attached mid-thread, realpath cwd comparison). `tools/list` snapshots and the golden replay are re-recorded for the new tool, the receipts `kind` filter, the health fields, and an unwaited switch's `tokenUsage: {next: null, reason: "not_waited"}`.
- Role handover and the `orchestrator` role (design doc R7.20, T-7.9, R1.21).
  - An open `reply` / `action` message sent to `role:<name>` follows the role. When the role moves to another session before the message is resolved, the new holder sees it (`read_agent_link_inbox` new and open mail, hook notices, the Code channel), gets the remaining reminders (the count carries over; the cap holds), and may resolve it; the previous holder no longer sees it and gets `wrong_recipient`. The sender's status and waits keep working: `get_agent_link_message_status` adds `via` and `holder` for messages sent to a role, the role's current holder may read the status, the resolution's `by` is the resolver's address, and a wait returns the new holder's reply. Mailbox lines are never rewritten; the recipient is derived at read time from `roles.json` and the holder address that sends now record (`metadata.role.address`). A cleared role, an `fyi` message, or a message sent through a role before this change stays with the session it was sent to; a resolved message stays with its resolver. `reminded` events record `to`, so the `Stop` hook's once-per-interval gate is per recipient. A handover is a fresh delivery: the new holder gets it as new mail even when the previous holder already had it (deliveries now record `to`): hook notices on each prompt until it reads its inbox, as for any new mail, and one channel push; the same applies when the role moves back to a holder that never saw it (A to B to A), and a message that reached the cap under the previous holder shows in the new holder's open mail; the count and cap are unchanged. A send with `replyToMessageId` credits the authenticated caller (current session, `CLAUDE_SESSION_ID`, or the Codex runtime context), so a Codex thread that takes over a role can resolve by replying with `message_claude_session`; `reply_agent_link_message` and an inbox for Codex wait for B7b. Codex holders get reminder turns when enabled.
  - The project orchestrator is the `orchestrator` role, scoped by project root. `set_agent_role` and `clear_agent_role` take an optional absolute `projectRoot`, for the `orchestrator` role only, stored as `roles.orchestrator.projects` in `roles.json` (validated on read; `projects` on any other role is ignored and reported; role views show `projects`). `resolve_project_orchestrator` and the tools built on it use, in order: (1) an explicit `orchestratorThreadId` (a thread id, or `role:<name>`); (2) the Codex thread the user assigned the `orchestrator` role for this project (`set_agent_role({role: "orchestrator", agent, projectRoot})`, stored as `roles.orchestrator.projects` in `roles.json`); (3) the project's binding file (a binding whose thread cannot be read still falls back to search, `binding-unreadable-search`, never to a role); (4) the `orchestrator` role's own holder, only when `projectRoot` was given and the project has no binding file; (5) ranked search. A call with only a query never uses the role's own holder, and a role decision never carries a binding's `projectId`. Project roots are matched by `path.resolve`, the same as binding files: no symlink resolution and no subdirectory matching. Only the `orchestrator` role takes a `projectRoot`. A holder that is not a Codex thread, or whose thread cannot be read, is skipped. Results add `source: "role"` and `role`, and sends to a role-resolved orchestrator are role-addressed for enforcement. Under `warn`/`enforce`, a direct send to a thread that holds the orchestrator role only per project gets `replacement: "message_project_orchestrator"` and `details.projectRoots`. Without an `orchestrator` assignment nothing changes.
  - Tests: `tests/claude/role-handover.test.js` (T-7.9: inbox, hook, channel, reminders with the count carried over and the cap, a role change mid-interval with racing hooks on stale tables, resolution and `wrong_recipient`, sender status and wait, a Codex holder) and `tests/codex/orchestrator-role.test.js`. The `tools/list` snapshots are re-recorded for `projectRoot` on the role write tools, the `resolve_project_orchestrator` description and `role` output, and `via` / `holder` on the status tool.
- Message labels, explicit replies, and resolution (design doc section 7, PR B7a). Codex receive, fork and reconcile, and switching on Codex reminder turns follow in B7b.
  - Labels: every message is labeled To, From, and Anticipation. `message_claude_session` and `reply_agent_link_message` take `anticipation` (`reply`, `action`, or `fyi`) and an optional `replyBy` (ISO 8601 with a time zone, at least 30 s ahead). The default is `fyi`, and `waitForReply: true` implies `reply`. An unknown anticipation, a malformed or too-early `replyBy`, `replyBy` with `fyi`, and `fyi` with `waitForReply` are `invalid_arguments`. Mail stored by earlier versions has no label and reads as `fyi`.
  - **Envelope change.** `<agent-link-message>` now always carries `anticipation`, plus `replyBy` and `inReplyTo` when set. The B2 attribute `replyTo` is renamed `inReplyTo`. `from` and `to` are addresses (`claude:<cliSessionId>`, `codex:<threadId>`, `external`, or `invalid`). The `<reply>` line is fixed text per anticipation (for example "A reply is expected. Call reply_agent_link_message with messageId=... and resolution "reply", or "decline" with a reason."). Codex turn envelopes keep their direct reply line until B7b and are labeled `reply` when the sender waits for a reply, `fyi` otherwise. The `<notice>` text is unchanged. Hook notices and the channel event meta (`from_session_id`) show addresses too.
  - No automatic replies: a `reply` or `action` message is open (`pending`) until the recipient resolves it. Delivery, an inbox read, a channel event, or an unrelated message never counts.
  - `reply_agent_link_message` gains `resolution`: `reply` (default, `message` required), `decline` (`message` is the required reason), or `done` (optional note). Only the recipient may resolve (`wrong_recipient`). A message resolves once: a second resolution is the new error code `already_resolved` (`details.messageId`, `status`, `resolvedAt`). An `fyi` message takes only `reply`, which sends a reply and sets no status. The reply is itself a labeled message. Results add `resolution`, `status`, `late`, and `anticipation`; `messageId` is null for `done` without a note, with `delivery: "none"`. Each resolution writes one receipt with a `resolution` block (`{kind: "resolution", messageId, resolution, by, at, late}`).
  - A send with `replyToMessageId` (or a reply written by a 0.5.x server) resolves an open message as `replied`.
  - Status for `reply` / `action` messages is computed from the mailbox and the clock: `pending`, `replied`, `declined`, `done`, `unresolved` (the reminder cap was reached and one more interval passed), or `expired` (`replyBy` passed). `unresolved` and `expired` still accept a late resolution (`late: true`). One receipt is written per transition (new receipt action `message_status`), by a wait or the server's claim sweep.
  - Re-surfacing on Claude: while an open message is delivered and `pending`, the recipient is reminded only between turns, at most once per `AGENT_LINK_REMINDER_INTERVAL_MS` (default and minimum 30000), up to `AGENT_LINK_REMINDER_LIMIT` (0..20, default 3) times. The `UserPromptSubmit` hook adds a fixed reminder notice (addresses and numbers only, never a body). A new `Stop` hook in `hooks/hooks.json` returns `{"decision": "block", "reason": <notice>}` when a reminder is due, at most once per interval per recipient, and never when nothing is due, so a turn can always end. Reminders never use a channel push or `turn/steer`. Each reminder is claimed before it is shown (marker files in `<mailbox>.claims/`), so concurrent processes show it once.
  - New read-only tool `get_agent_link_message_status({messageId})` for the sender or the recipient (anyone else: `permission_denied`, `reason: "not_participant"`): `{messageId, from, to, anticipation, replyBy, inReplyTo, delivery, status, resolution, reminders}`, never a body.
  - Message waits (`message_claude_session` with `waitForReply`, `wait_for_claude_session` with `replyToMessageId`) end when the message leaves `pending`: `outcome` `reply`, `declined`, `done`, `unresolved`, `expired`, or `timeout`, with `messageStatus`. Only the explicit reply, decline reason, or done note is returned, enveloped. `message_codex_thread` `waitForReply` is unchanged in this release (turn completion; moves to explicit replies in B7b).
  - `read_agent_link_inbox` also shows delivered `reply` / `action` messages that still await resolution, after the new ones (`includeOpen`, default true; `openCount`; `open: true` on those entries). Inbox, inspect, and wait message objects add `anticipation`, `replyBy`, `inReplyTo` (`replyTo` stays as a deprecated duplicate), `status`, `resolution`, and `reminders`.
  - Codex reminder turns (`turn/start` with `turnTrigger: "agent-link-reminder"`, text exactly the reminder notice, idle threads only, never `turn/steer`) are implemented behind `AGENT_LINK_CODEX_REMINDERS=1`, off by default until the Codex turn-completion signal is verified (B7b).
  - `agent_link_health` adds `reminders: {limit, intervalMs, codexTurns, warnings}`; an interval below 30000 or a limit outside 0..20 is ignored and listed in `warnings`.
  - Exactly-once state across processes. Every writer of a resolution (`reply_agent_link_message`, a send with `replyToMessageId`, a wait settling an older-style reply) first takes a `resolve-<messageId>` claim (an exclusive create in `<mailbox>.claims/`) and re-checks under it, so concurrent resolvers yield one success and `already_resolved` for the rest; a claim left by a crashed resolver is superseded after 10 s. Only a `resolved` event written for the stored recipient counts. A reminder claim counts toward the cap even if its `reminded` event was never written (a crash in between), so the message still reaches `unresolved`. Concurrent `Stop` hooks share a per-recipient slot claim, and `stop_hook_active` is checked as a second guard. A message the recipient already answered with an older-style reply row is not reminded. The hook reads the mailbox once per run (20k rows with 2,000 due: about 0.2 s), and the claim sweep rotates its starting point between passes.
  - Claim files are collected by the server (shortly after start, then hourly, at most 500 per pass, only when a mailbox exists): claims of resolved messages, reminder claims whose event exists, and old orphans. The claims directory is tightened to 0700. The same pass writes the once-only receipt for messages that became `unresolved` or `expired`; `get_agent_link_message_status` writes nothing.
  - Tests: `tests/claude/reply-model.test.js` (T-7.1 to T-7.8 and T-7.10 with an injected clock, orphan claims, the Stop slot, claim collection), `tests/claude/resolution-race.test.js` (4 processes racing to resolve one message, 12 trials per case), `tests/codex/reminder-turns.test.js` (Codex reminder turns against the stub app-server, which now answers `thread/read` and logs `turn/start` / `turn/steer`). The `tools/list` snapshots and the Codex golden replay are re-recorded for the envelope, address, label, and health changes.
- User-assigned roles (design doc section 1.8, PR B9). Additive.
  - `role:<name>` addresses (`[a-z0-9-]{1,40}`): `message_codex_thread` `threadId`, `message_claude_session` `sessionId` (or `query`), and `resolve_agent` `query` resolve a role to its current holder when the call runs. No holder is `not_found` with `details.role`; a hand-edited role listing several holders is `ambiguous`; a role held by the other harness is `invalid_arguments` with a hint naming the right tool. `list_agents` and `resolve_agent` sessions gain `roles[]`.
  - Role table `<state>/roles.json` (0600, directory 0700): `{version, enforcement?, roles: {<name>: {address, assignedAt}}, overridePolicy}`, written only by the role write tools. Each write takes a lock file (a stale lock of a dead process is removed only by the holder of an exclusive breaker file, after checking it is still the same stale file; a busy lock fails fast after 250 ms with a retry hint) and replaces the file atomically (temporary file, fsync, rename). Writes change only the keys they own on the raw JSON, so entries Agent Link does not understand survive, and a file whose `version` is not 1 is never written. Hand edits are validated on every read; invalid entries are ignored and reported, and a file that is not valid JSON fails role lookups with `state_io_error`, reads as an empty override policy, and makes role enforcement fall back to its default (fails open). Read-only tools never write.
  - Procedures: `<state>/roles/<name>.md` (regular file, at most 64 KiB; symlinks, FIFOs and devices are refused), versioned by SHA-256 (a hand edit or `set_agent_role` with new `procedure` text is the next version, once, assigned on the next send or set). Versions and deliveries live in Agent Link's own `<state>/role-state.json`; delivery is tracked by the text's hash, so a holder gets each distinct text once, also after a role is recreated. A send to a role whose procedure file was refused (a symlink, FIFO, or file over 64 KiB) still goes out without it, with a `role_procedure_unavailable` warning and a `roleProcedureWarning` receipt field. Messages to a role carry `via="role:<name>"` and `procedure="<name>@<version>"` in the envelope; the first delivery of each version to a holder also carries the text in a `<procedure>` element outside `<body>` (escaped and capped like a body). Send results return `via` and `roleProcedure: {name, version, textIncluded}`; receipts record `via` and `roleProcedure`.
  - New tools: `set_agent_role({role, agent, procedure?})`, `clear_agent_role({role})`, `list_agent_roles()`, `get_agent_role({role, includeProcedure?})`, `set_agent_override_policy({target, model?, effort?, cwd?})`, `get_agent_override_policy({target?})`. The three write tools are `destructiveHint: true` and are refused with `permission_denied` (`reason: "role_admin_disabled"`) unless the user starts the server with `AGENT_LINK_ROLE_ADMIN=1`; no tool argument or message can enable it.
  - Role enforcement plumbing (section 1.9): `AGENT_LINK_ROLE_ENFORCEMENT` (`off`, `warn`, `enforce`), then `roles.json` `enforcement`, then the default `off`. `message_codex_thread` and `message_claude_session` run the check: under `warn`, a new message between two role holders sent to an address instead of `role:<name>` gets a `direct_coordination` warning and a `direct-coordination` receipt tag; under `enforce` it is `permission_denied` (`role_address_required`) and nothing is sent or written. Replies and messages with a non-role holder at either end are exempt. **This release ships `off`; nothing changes unless a user sets it.** `AGENT_LINK_ROLE_ADMIN` and `AGENT_LINK_ROLE_ENFORCEMENT` are removed from the managed Codex app-server's environment. `agent_link_health` adds `roles: {path, exists, count, assigned, policyTargets, enforcement: {mode, source, ignored}, admin, problems, error}`.
- **In-place overrides on existing Codex threads (design doc section 9.2, R9.4, R9.5, R9.13).** `message_codex_thread` (and the orchestrator and handoff tools built on it) decide every `model`, `effort`, and `cwd` for an existing thread in one place. A value equal to the thread's own is forwarded. A different value is allowed when the session that launched the thread through Agent Link changes its effort, when the target's override policy allows the sender (`roles.json` `overridePolicy`, keyed by address or `role:<name>`; senders are addresses, `role:<name>`, or `"*"`, never matching `external`; `model` covers `modelProvider` and `serviceTier`), or, until 0.7.0, when the caller passes `allowTargetOverride: true`. **The flag is deprecated**: every use adds a `deprecated_argument` warning naming 0.7.0 (when it stops granting anything) and the replacement (a new thread or fork for a model, the launcher for effort, the override policy otherwise); it is rejected from 0.8.0. Otherwise the change is refused with `permission_denied` and `reason` `model_switch_requires_fork_or_opt_in`, `effort_not_permitted`, or `cwd_change_not_permitted` (replacing `target-override-rejected`; `details.conflicts` is unchanged). An allowed change persists, no revert is sent, and the result lists it in `switches: [{setting, previous, current, grantedBy: launcher|policy|allowTargetOverride, policy?, persists, expectedCost}]` (`expectedCost.basis` is `unknown` until token usage is recorded) plus a `model_switch`, `effort_change`, or `cwd_change` receipt (`override` field; new `list_agent_link_receipts` `action` values). **Behavior change:** a cwd change must be absolute and stay inside the thread's workspace (the git top level of its cwd, or the cwd itself, symlinks resolved), otherwise `invalid_arguments` or `cwd_outside_workspace`, even with the policy or `allowTargetOverride`. Unlike 0.4.0, `allowTargetOverride` with a `cwd` on a thread that does not report its own cwd is now refused (`cwd_outside_workspace`): without a reported cwd there is no workspace to check against (R9.5). Any override aimed at a Claude session (for example a role held by one) is `unsupported` (`capability: "turn_overrides"`). `launch_codex_thread` receipts record `launchedBy` (the caller's runtime address, or null for an external caller), which is how the launcher is recognized; a launch receipt written before this field existed counts only when a Codex-host server took its origin thread from the runtime caller context.
- Scripts: `npm run check:approval-config` no longer reads the real Codex config by default. Without either it exits 2 without reading anything.

## 0.4.0 - 2026-10-06 Routing, Codex correctness, and hardening

- Security: the managed Codex app-server no longer listens on an unauthenticated `ws://127.0.0.1` port. It listens on a Unix socket, `<pid>.sock`, one name per Agent Link process, in a state directory that must be a real directory (not a symlink) owned by the user and is tightened to 0700. When the state path is too long for a socket, the socket goes in a private `agent-link-<uid>` directory under the per-user temp dir on macOS or `/tmp` elsewhere, with the same checks. Where Unix sockets are unavailable (Windows, or `CODEX_AGENT_LINK_APP_SERVER_TRANSPORT=ws-token`) it uses a loopback websocket with `--ws-auth capability-token` and a 0600 token file. The free-port probe is gone from the default path.

A value that differs from one the thread reports is refused (`cwd` is compared by real path, so `/tmp` and `/private/tmp` match). ## 0.2.3 - 2026-09-28 Idle cost and app-server lifecycle

Measured live on 2026-09-28: each idle agent-link server used 12-56% of a core,
and `codex app-server --listen ws://127.0.0.1:<port>` processes were left with
parent = launchd. With ~15 sessions open the load average reached 170.

**Idle CPU (the channel bridge).** The Claude channel bridge ran every second
and re-resolved the current session each time. That walked the whole session
corpus and regex-scanned every `ps` line for every session, about 280 ms of CPU
per tick. Changes:

- The session is resolved once and cached, because it never changes for a
  server's lifetime.
- An unchanged mailbox is skipped with one `stat()` on (ino, size, mtime).
- The poll interval backs off exponentially from 1 s to 30 s while there is
  nothing to deliver. `fs.watch` on the mailbox directory wakes it at once
  when a message lands.
- `listClaudeSessions` filters `ps` to `claude ... --resume` lines once per
  call instead of once per session. Output is byte-identical: checked on all
  595 local sessions, including synthetic loaded and near-miss lines.

Result (`scripts/idle-churn-measure.js`, 120 s idle, real session corpus):
23.4% CPU before, 0.3% after.

**Managed app-server lifecycle** (`src/codex/app-server-client.js`,
`src/server.js`):

- Idle servers never start an app-server. The first real tool call starts one
  (lazy, unchanged) and later calls reuse it.
- Connect and spawn are single-flight. Before this, concurrent first calls
  could each spawn an app-server, and the first handle was overwritten and
  never killed.
- An idle timeout (5 min by default; `CODEX_AGENT_LINK_APP_SERVER_IDLE_MS`,
  0 disables) stops the app-server. The next call starts a fresh one.
- The app-server is spawned `detached`, so it leads its own process group.
  Every stop signals the whole group: SIGTERM, a bounded wait, then SIGKILL for
  the leader and any members still running.
- Shutdown on SIGTERM, SIGINT, SIGHUP (new) and stdin end/close now waits for
  that cleanup (hard limit 4 s) before exiting. Before, SIGTERM exited without
  waiting, stdin end never exited, and SIGHUP left the app-server orphaned.
- A startup that never becomes ready is killed as a group, not leaked.
- Orphan reaper: each spawn writes
  `~/.claude/agent-link/managed-app-servers/<pid>.json`
  (`CODEX_AGENT_LINK_STATE_DIR` overrides the location). At server startup and
  before a spawn, any record whose owner is dead is acted on. Its process group
  is killed only if the recorded pid still runs an `app-server` command with
  the recorded URL, so a reused pid is never signalled.
- `src/app-server-client.js` now re-exports `src/codex/app-server-client.js`.
  It was a byte-identical copy.

Tests: `npm run test:codex-lifecycle` (stub app-server; never launches
Codex.app) and new channel-bridge cases in `npm run test:claude`.

## Unreleased - 2026-08-06 Cross-device archive (EXDEV) fallback

`archiveLocalThread` moved threads into `archived_sessions` with a bare
`fs.rename`, which throws `EXDEV` when `archived_sessions` is a symlink onto a
different volume (for example when the archive is offloaded to an external drive). The rename is
retained as the fast path; on `EXDEV` the move falls back to copy → same-volume
atomic promote → unlink:

- The copy stages under a `.exdev-tmp-<pid>` name so `.jsonl` discovery never
  observes a partial transcript, then promotes with an atomic same-volume rename.
- Source `mtime` is preserved onto the destination — thread list ordering sorts
  by it.
- On any fallback failure the staging file is removed and the source is left
  untouched; the operation is retryable.
- New regression: `scripts/archive-exdev-regression-test.js` exercises a real
  cross-device `archived_sessions` symlink (skips cleanly when no second volume
  is mounted). Note: Codex Desktop's *native* archive/unarchive
  (`codex-rs/thread-store`) still does a bare rename and will surface EXDEV as a
  recoverable error dialog; archiving through agent-link tools is the supported
  path while the archive lives off-volume.

## Unreleased - 2026-07-31 Session-index poll cost

The Claude Channel bridge polls `listClaudeSessions()` once per second, and that
call re-read the entire session corpus on every tick. On this machine that was
841 MB of transcripts plus ~4 MB of sidecars per tick, measured at **2071 ms per
call** — twice the poll interval, so the bridge ran permanently backlogged and
pinned a core (~90% CPU per Claude Code session, and it spawns one per session).

- **Transcript reads are now bounded.** `parseTranscriptSummary` only ever needed
  the opening record — the existing loop breaks on the first parseable line — but
  `fs.readFileSync` + `raw.split("\n")` had already materialized the whole file,
  up to 39 MB each. It now reads a bounded 64 KB prefix via `fs.readSync`, growing
  (capped at 4 MB) only when the prefix contains no parseable line at all. The
  trailing partial line is discarded, which also drops any UTF-8 sequence the byte
  boundary split.
- **Repeat parses are cached.** Transcript summaries and sidecars are memoized on
  `(mtimeMs, size)`, so unchanged files cost one `statSync` per tick instead of a
  full read and `JSON.parse`. Malformed sidecars are deliberately not cached, so
  they still throw and are skipped exactly as before.

Steady state drops from 2071 ms to 111 ms per call (18.6x), and sustained 1 Hz
polling from >64% of a core to ~10.6% — the bridge now keeps pace with its own
interval. Verified behaviour-identical against the previous implementation across
all 595 local transcripts and 197 resulting sessions: zero field differences, and
the cached pass matches the cold pass exactly. Full `test:claude` suite green.

Known issue, not changed here: `lastActivityAt` is set from the *first* record's
timestamp, but `listClaudeSessions` sorts by it as a recency key. Sessions are
therefore ordered by start time, not last activity. Fixing it means switching the
field to `stat.mtimeMs`, which changes list ordering, so it is left for a
deliberate change.
